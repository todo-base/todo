# Виды

## Назначение

Хранилище может доставлять два вида данных: **source** и **view**.

**Source** — это исходные данные по issues, наборам, их атрибутам и т.д. К ним
применяются правила непротиворечивости, несовпадения и определения единственного
источника правды (single source of truth).

**View** даёт представление уже существующих исходных данных. Он может
переопределять атрибуты, состав наборов и некоторые другие параметры, но не
изменяет source-данные.

Например, общий список задач в хранилище — это source-данные. Текущее размещение
задач на доске — может быть view. План с выбранными задачами на спринт — также
может быть представлен отдельным view.

Разные view могут по-разному представлять одни и те же source-данные.

## Модель

### Что переопределяет view

View оперирует ссылками на сущности source и может задавать поверх них:

- **состав и группировку наборов** — какие задачи попадают в набор и в какие
  наборы они сгруппированы (например, по статусу, исполнителю, тегу);
- **порядок** — сортировку задач и наборов внутри представления;
- **фильтрацию** — какие задачи скрыть или показать;
- **переопределение атрибутов** — значения атрибутов, действующие только в
  рамках данного view (source при этом не меняется).

View **не создаёт** новые задачи как источник правды: всё, что он отображает,
существует в source. Если во view упомянута сущность, отсутствующая в source, —
это рассматривается как ошибка несовпадения.

### Связывание с source

Задачи и наборы связываются между source и view по идентификаторам или именам:

- задача — по `id`, если он указан во view, иначе — по имени;
- набор — по идентификатору набора или при отсутствии явных id набор сопоставляется
  по пути заголовков (`Set 1/Sub set 1.1`).

Связывание по имени допускается как удобный вариант для рукописных view, но
слудует учитывать, что оно неустойчиво к переименованиям.

### Семантика разрешения

Итоговое представление вычисляется как наложение view поверх source:

```
result = apply(view_overrides, source)
```

Правила:

1. **Переопределение атрибутов** — для каждой задачи берётся значение атрибута
   из view, если оно задано, иначе из source.
2. **Состав наборов** — наборы view полностью определяют группировку
   отображаемых задач; задачи, не упомянутые во view, в него не попадают
   (если не включён режим показа остатка — см. открытые вопросы).
3. **Несовпадения** — ссылка во view на несуществующую в source задачу/набор
   считается ошибкой целостности и сообщается пользователю; view при этом не
   становится источником правды для такой сущности.
4. **Идемпотентность** — повторное применение view к неизменному source даёт
   тот же результат.

## Поддержка видов в tracker-fs

Файловый трекер чётко отделяет source-данные от view.

### Атрибут `kind`

Тип данных задаётся атрибутом `kind` — по аналогии с базами данных, где view
строится поверх базовых данных. Допустимые значения:

- `source` — исходные (source) данные; значение по умолчанию, явно указывать не
  обязательно;
- `view` — представление; для view-файлов атрибут **обязателен** (может быть
  установлен в самом файле или назначен ему при обработке).

Значение `view` может быть указано в пути к файлу в одном из двух вариантов:

- суффикс в имени файла: `TODO.view.md`;
- выделенный подкаталог: `view/TODO.md`.

Source-файлы (`TODO.md`, `Project.toml`, `*.manifest.md`) и view-файлы трекер
различает по размещению или по явно указанному атрибуту `kind`; при конфликте
приоритет имеет `kind`, указанный извне: назначенный программой или взятый из
пути.

```md
---
kind: view
group_by: status
---

# ToDo
...

# In Progress
...
```

### Атрибуты вида

Помимо `kind`, view-файл может содержать управляющие атрибуты:

| Атрибут    | Назначение                                                          |
|------------|---------------------------------------------------------------------|
| `kind`     | `view` (обязателен)                                                 |
| `from`     | ссылка на источник (source); по умолчанию — source текущего проекта |
| `group_by` | атрибут, по которому задачи группируются в наборы                   |
| `order_by` | атрибут(ы) сортировки задач/наборов                                 |
| `filter`   | условие отбора задач во view                                        |

## Примеры

Source (`TODO.md`):

```md
- top task A

# Backlog

- task 1
- task 2
```

View «доска по статусу» (`board.view.md`):

```md
---
kind: view
group_by: status
order_by: priority
---

# ToDo

- task 1

# In Progress

- task 2
```

## Открытые вопросы

- Формальный синтаксис `filter` и `order_by`.
- Режим показа задач, не вошедших ни в один набор view (остаток).
- Ссылка `from` на внешний проект/несколько источников.
- Поведение при переименовании набора без явного id (связь по пути заголовков).
